# seedy

a fabric mod for minecraft 26.2 and 26.3, built with stonecutter. the resizable dear imgui panel is rendered inside minecraft's window by a jni-loaded native library. the world tab controls matching-loot chest outlines.

## install and use

put the matching jar from `artifacts/` in your mods folder. use java 25, fabric loader 0.19.3 or newer, and fabric api 0.161.0 for your minecraft version. remove any older seedy jar before installing this one.

the mod id is `seedy`. the jar includes its icon, author, and project links in fabric metadata so prism can show them in the mods list. refresh the list after replacing an older jar.

0.9.18 reduces the gameplay overlay's rendering overhead. its commands join minecraft's existing submission, and its vulkan render area follows the visible hud instead of covering the whole framebuffer. there are no per-frame native queue submissions, fence waits, or framebuffer allocations. unchanged hud snapshots stay cached across jni calls, panel data is built only when requested, and structure collection runs through a budgeted queue. matching-loot outlines use reusable projection storage. the optional command-line vulkan benchmark checks real gpu rendering and pixel output without launching minecraft; its timings are not an in-game fps measurement.

press f8 in a world to toggle the panel, or run `/seedy`. change the key in options → controls → key binds → seedy. escape also closes the panel. drag its top header to move it and its bottom-right corner to resize it. the jar contains a universal macos dylib and a windows x64 dll. select vulkan in video settings and restart minecraft, or use mcopt's metal renderer on a supported apple silicon mac with minecraft 26.3. the native library shares the active renderer's device and frame command buffer; it does not create another window or graphics context.

the recovery tab lists detected structures, start chunks, evidence, and search progress. collection recognizes desert-pyramid traps, swamp-hut interiors, shipwrecks, and trial-chamber starting rooms. shipwreck and trial detection uses the target version's vanilla templates, including shipwreck wood palettes and all rotations. the starting room of a trial chamber must be loaded; a random corridor or spawner is not enough to determine its start chunk. select the observations you trust, then press recover seed. a structure search needs five independent observations and 40 evidence bits. more observations help narrow it. trial chambers provide fewer lower-bit constraints than shipwrecks or pyramids, so a search may ask for more evidence even after meeting the minimum. manual entry accepts supported random-spread structures; enter the actual start chunk, not the chunk you happen to be standing in. the world generation version is a separate setting from the client and the server's reported protocol version. use the version that generated the chunks; location and map searches require the matching seedy jar.

enter a signed 64-bit seed in the seed tab, or recover it from observations. the locate tab searches vanilla structures and biomes in the overworld, nether, and end. the radius now reaches 1,048,576 blocks, with 8k, 32k, 128k, 512k, and 1m presets. searches check nearby regions first and keep up to 256 nearest confirmed matches. wide scans stop after 100,000 candidates or two minutes and clearly report partial coverage. choose a dimension to see its available targets. nether fortresses and bastion remnants can be searched separately; nether complexes returns both. coordinates and distances use blocks in that dimension; use position is disabled while you are in a different dimension, and coordinates are not portal-scaled. you can cancel searches and copy coordinates. changing the search inputs clears the previous results. type in target dropdowns to filter names. use save beside a result to keep it in the saved tab, where distance and compass direction update as you move in the same dimension.

## mcopt

0.9.19 adds an optional metal path for [mcopt](https://github.com/noahdunnagan/mcopt). use the 26.3 seedy jar with mcopt 0.3.0-alpha.2 and fabric loader 0.19.5 or newer. keep fabric api installed for seedy. mcopt itself requires apple silicon and macos 26 or newer, and its current release does not support minecraft 26.2. seedy's 26.2 jar continues to use vulkan.

the panel, f9 hud, and matching-loot chest outlines render after mcopt applies pending clears and before it presents the frame. this includes its queued-present modes. the metal path uses mcopt's existing command buffer and leaves submission and waiting to mcopt. the compatibility hooks are disabled when mcopt is absent. when mcopt's metal renderer is switched off, use vulkan. the seed recovery engines do not depend on the graphics backend.

the command-line compatibility checks use the released mcopt jar: a loader probe applies the real fabric mixins and stops before minecraft's main method, while a render probe runs seedy's jni renderer on mcopt's actual native command buffers and reads back the hud and panel. these checks do not measure live gameplay fps or replace an in-game compatibility test. run the `mcoptLoaderProbe` and `mcoptRenderProbe` gradle tasks on 26.3 with `-PmcoptJar=/absolute/path/to/mcopt.jar` to repeat them.

## seed map

the interface uses a charcoal palette with black accents, a subtle background grid, map-first navigation, and grouped controls. village markers use house symbols; end cities with elytra ships use wing symbols. selected structures get a visible ring, and the location panel lets you copy coordinates or center the map. biome labels stay distinct from structure labels.

seedy opens as a larger floating window inside minecraft. resize from any edge or corner, drag the header to move it, and use expand/restore or double-click the header to maximize it inside the game. settings offers compact and large layouts, opacity, sidebar width, and map defaults. size, position, selected tab, and display settings save to `config/seedy/ui.json` and are restored next time.

the map has a collapsible sidebar with a draggable divider. choose fast, balanced, or detailed sampling; detailed allows more tiles before reducing resolution. toggle biome and structure names, player markers, coordinate or chunk grids, and adjust marker size and scroll sensitivity. the biome legend lists visible biomes; click one to highlight it. follow keeps the map centered on your player until you pan or scroll. smaller windows stack the controls above the map.

the zoom slider and six presets cover 0.125 to 1,024 blocks per screen pixel. shift-scroll gives finer zoom steps. close-up views show structure coordinates, while the footer reports visible area and actual biome sampling distance. close-up sampling uses minecraft's block-level biome blending and can reach one block per sample. right-click the map to copy coordinates, center a position, or zoom there. chunk lines appear once they are far enough apart to read. the fast, balanced, and detailed modes allow up to 64, 192, and 512 visible biome tiles respectively, with bounded caches for 1,024 biome tiles, 256 structure tiles, and 16,384 terrain heights.

the map tab shows biome colors and a selectable structure layer for the overworld, nether, and end. drag the map to pan, scroll to zoom around the cursor, or use the plus and minus buttons. enter x and z and press enter to jump somewhere; player brings you back to your position in the selected dimension. hover for biome names and structure coordinates, then click to select a location and copy it. end cities can be filtered by elytra ship, with ship markers shown in gold.

the base colors show a biome slice at the chosen y. optional terrain shading uses vanilla-predicted ground heights, with smooth lighting across tile edges. coastlines can be enabled separately. biome colors arrive first, then terrain shading fills in on the background worker. change y to inspect underground biomes. small biomes can disappear at wider zoom levels; zoom in for finer sampling. dots use the same vanilla structure-generation checks as locate. wide views show the nearest 256 confirmed structures in the visible search area instead of hiding the layer. the footer distinguishes this overview from a complete local scan. selecting a different layer changes the structure dots without resampling cached biomes.

visible tiles load on one low-priority background worker, with a short delay after navigation. recent tiles are cached with fixed limits, and leaving the tab or closing the panel cancels pending work. the map reuses the vulkan panel renderer, without a browser or separate graphics context. it predicts vanilla generation without loading world chunks. village dots use minecraft's validated starting piece and terrain/biome checks without building every street and house; other structure dots generate their pieces, including end-city ships and stronghold portal rooms.

## gameplay overlay

press f9 to toggle the gameplay overlay. its key can be changed in minecraft controls. settings → gameplay overlay controls scale, opacity, corner anchoring, and which rows appear: coordinates, facing, biome, dimension, frame rate, recovery progress, collected evidence, a tracked location, and the seed value. the seed value is hidden by default. use edit overlay position in settings to drag it somewhere else. labels on the overlay use normal capitalization.

use track on a search result or map selection to show its distance and direction while playing. nearest-result tracking can be enabled too. the overlay does not take mouse or keyboard input during gameplay, follows minecraft's hide-hud setting, and uses the existing vulkan renderer. closing the panel cancels map generation; keeping the small overlay visible does not keep the map worker running.

## end cities

choose end → structures → end cities. the end cities filter offers all cities, with elytra ship, and without elytra ship. seedy generates the city pieces and checks the elytra marker in the ship template instead of estimating ship presence from the placement grid. each result shows its ship status, and copy elytra copies the generated item-frame coordinates. city results include height. this predicts fresh generation; it cannot tell whether another player has already taken an elytra.

## chest loot

choose ancient cities or desert pyramids in locate, then enable predict chest loot. add an item and its minimum total per structure. for example, enchanted golden apple with a minimum of 3 shows structures with at least three predicted apples across their chests. you can combine up to eight different items; every minimum must be met. remove all filters to browse every structure's chests. select a result's coordinates to see item totals and each chest's contents, including enchantments and durability. copy chest copies its coordinates.

purple outlines mark loaded chests containing your selected items in matching search results. they appear when the chunk loads, disappear when the chest is broken or unloaded, and clear when the seed or search changes. ancient-city chests use their full generated coordinates; desert-temple chest heights are resolved from the loaded treasure-room blocks. these are the only world outlines, and they have no black backing stroke.

predictions use the current version's vanilla templates, decoration random sequence, loot tables, and enchantment functions. version 0.5.1 evaluates loot pools directly, fixing the null server-level error caused by fabric's server-only loot-table events during client-side predictions. they describe fresh, unopened chests with normal player luck. already looted chests, changed loot tables, and older generated chunks can differ. a sculk feature can consume a terrain-dependent number of random draws before a later chest in the same chunk. those affected chests are marked as unavailable and excluded from totals rather than given guessed contents; in those cases the displayed total is a minimum, and the filter can miss a structure whose remaining items are in an unavailable chest. chests in ice boxes and the fixed chest in applicable city-center templates are included. no chest is opened or modified to generate a prediction.

## saved progress

observations, collection settings, seeds, and saved locations are stored under `config/seedy/sessions/`. files are separated by minecraft version and the world seed hash. no server address is stored. progress saves every five seconds and when disconnecting or closing minecraft; the footer shows its status. damaged save files are left unchanged. saved locations are shown only for the current seed.

loaded chunks are checked immediately, and matching observations appear in the panel without waiting for the rescan queue. neighboring templates are retried as each chunk arrives. rescan checks currently loaded overworld chunks again within a per-tick time budget. detection still needs the recognizable part of a structure: missing or unloaded blocks never count as evidence.

the world tab lists mob spawners and buried-treasure candidates in loaded chunks without drawing outlines for them. treasure detection checks the single chest at local chunk position 9,9, its biome, waterlogging, and supporting terrain. these are candidates, since a player-placed chest can match the same pattern. this feature does not read unopened chest contents or add treasure/spawners as recovery evidence.

## recovery engine

seedy owns the observation store, random-number implementation, bit lifting, candidate search, cancellation, and seed-hash verification. seedcrackerx and the seedfinding libraries are not runtime dependencies or bundled engines.

the algorithm filters 19 lower structure-seed bits, searches the remaining 29 bits, and checks the upper 16 world-seed bits against the server's sha-256 seed hash. a separate inverse-random search handles rejected draws that ordinary low-bit filtering can miss. candidates are checked against every observation.

the research reference is [seedcrackerx](https://github.com/19misterx98/seedcrackerx), revision `b72a829f768967fa737a4f1f63b32e37b9619152`. its source and license remain under `vendor/` for reference only. placement metadata and biome generation come from the target minecraft version.

seedy also scans bedrock, deepslate, and ore-vein blocks in overworld chunks already sent to the client. press recover seed to use the collected data automatically. seedy chooses available nether bedrock, overworld blocks, or selected structure observations without starting a search on its own. its bundled [bedrockseed](https://github.com/someone12469/seed-cracking) solver checks all collected chunks, keeps every natural raw ore position, and requires a world seed hash match before accepting a result. walking to structures is not required when the loaded area contains enough untouched block data. bedrock and positive deepslate observations narrow the random state using positional output bounds. negative stone observations are excluded because ore hiding and later generation can replace deepslate with stone. candidate states must also reproduce the observed raw ore positions using the selected generation version's vein noise before the expensive world seed scan starts. the 26.3 jar includes a 26.2 ore noise profile for older generated chunks; set the world generation version accordingly. the final scan uses up to six cpu workers and stops after a hash-verified match. block, structure, nether, and paper-salt searches require a manual start and cannot overlap. pause collection also pauses both block collectors. overworld scanning waits while its solver is running. stop search cancels all recovery engines; cancellation reaches block preparation, bit searches, the constraint solver, candidate hashing, and queued workers. a cancelled search stays stopped until another manual start. conflicting or insufficient evidence ends with a diagnostic saved under `config/seedy/recovery/`.
the block counter tracks raw iron and raw copper blocks in the ore-vein height range. ordinary iron and copper ore blocks are shown separately as candidates because they can also come from small veins. raw ore blocks are rare and clustered, so a loaded area can legitimately have none. chunk reloads refresh their samples, and rescan checks the loaded chunks again without double-counting old observations. changed or player-placed blocks can conflict with seed recovery, so untouched terrain works best.

in the nether, seedy scans loaded chunks for bedrock at y 4 and y 123. press check nether data to start the separate [nether bedrock cracker](https://github.com/19MisterX98/Nether_Bedrock_Cracker) search. its 48-bit candidates are checked against the server's seed hash to recover a full 64-bit world seed. only a hash-matched full seed is accepted; that same seed then powers seedy's overworld, nether, and end searches. the recovery tab shows the nether sample and search progress. this does not help before entering the nether, and modified bedrock, old chunks, or custom dimension seeds can prevent a match.

builds use the bedrockseed git submodule and bundle both native solvers and z3 for macos and windows in the same jar. run `git submodule update --init` before a source build. bedrockseed and z3 are licensed under mit. the nether bedrock cracker is licensed under lgpl 3. the bundled gcc runtime libraries carry the gpl with a runtime exception. their license texts are included in the jar.

the 0.9.11 jars include the block solver for apple silicon, intel macs, and windows x64. the panel is universal on macos and has a windows x64 build. the block-pattern pass uses exact integer thresholds, and the final inverse-rng kernel rejects guesses as soon as their carry bits contradict the known outputs. all forty added checks are necessary equations from the same xoroshiro additions; the original full output checks remain in place. native regression tests compare the optimized kernel with the original for 256 known rng states and 16,384 random search windows, including the candidate states they emit. those tests run on both mac architectures and windows in the build workflow.

a command-line replay of 1,000 chunks actually received from paper 26.2 with anti-xray mode 1 enabled recovered the correct, hash-verified seed in 224.7 seconds on an apple m3 with six recovery threads. only nine natural raw ore blocks remained visible. the solver received the chunk observations and seed hash, not the world seed. this is a measured packet replay, not a minecraft client test or a recovery guarantee for other worlds. the panel shows pass, stage, candidate progress, elapsed time, and an estimate during the final scan. all recovery checks wait for a manual start. some areas contain too little usable evidence, and hidden or changed blocks can still prevent recovery. windows builds use gcc with openmp; local intel builds use a small simd compatibility layer with clang.

## paper servers

paper can give each random-spread structure set its own placement salt, and its world settings can give generated features separate population seeds. with a verified world seed and observed start chunks, seedy checks whether the default placement fits each observed structure. select several starts from one structure set and press find placement salt to search its full signed 32-bit salt range. seedy stores a salt only when exactly one value fits every selected start, then uses it for that structure's locate results and map dots. if an observed start contradicts the default salt and no replacement has been recovered, seedy stops that structure search and tells you why instead of showing vanilla coordinates as paper results.

this does not recover unobserved salts, paper feature seeds, or unknown plugin world generation. a single start usually fits many salts. the world seed must first be recovered from trustworthy structure, overworld block, or nether bedrock evidence. paper feature seeds, anti-xray, modified bedrock, and edited terrain can make block-pattern evidence conflict; seedy reports that possibility after a failed check. no client-side method can promise a seed for every paper world from a fixed small area when the server withholds or randomizes the needed evidence.

## limits

structure searches apply vanilla placement, frequency, exclusion, weighted selection, valid-biome, and structure-start generation checks. the actual structure pieces are generated locally without creating terrain chunks. coordinates point to the first generated piece, not an unchecked candidate chunk. ancient cities and trial chambers include their generated underground height. other structures omit y because placement-time terrain adjustments can change it. results identify the structure's dimension. strongholds use vanilla concentric-ring placement, including biome relocation, and return the generated portal room with its y coordinate.

[chunkbase's seed map](https://www.chunkbase.com/apps/seed-map) was used as a reference for result semantics and limitations. the locator runs minecraft's version-specific world-generation code locally. worlds upgraded from older versions and custom data packs may differ from the current version's vanilla predictions.

biomes in each selected dimension are sampled every 64 blocks at the chosen y for nearby searches. wider searches adapt the sampling distance to keep work bounded; results state the actual spacing. the radius limit is 1,048,576 blocks and the result limit is 256. custom generation can invalidate predictions. modified or looted structures may not be detected. custom generation, older generated chunks, and structures removed or edited by players can differ from fresh vanilla generation.

## build and checks

run `bash scripts/build-macos.sh` on macos, or `powershell -file scripts/build-windows.ps1` from a visual studio x64 developer shell. then run `./gradlew :26.2:build :26.3:build`.

tests compare seedy's placement and hash calculations with minecraft, recover seeds from shipwreck-only, trial-only, and mixed observations, and check every shipwreck template palette and rotation, both trial start rooms, missing blocks, session persistence, random-draw rejection, cancellation, bounds, coordinate scaling, biomes, generated structure locations, stronghold portal rooms, treasure filtering, and outline clipping. seed `2589511696370800371` is covered by an ancient-city regression test on 26.2. run `ctest --test-dir native/build-overlay --output-on-failure` on macos for native clicking, text input, navigation, rescanning, saving and removing locations, copying, dragging, closing, outline toggles, loot filters, chest details, and unchanged outline colors. loot checks compare chest seeds against vanilla structure placement, compare item contents against vanilla loot-table codecs, and cover filter boundaries and chunk borders. the windows dll can be cross-compiled here; native windows execution and live exploration-to-seed verification still need testing. the vulkan backend uses dear imgui and volk, with their licenses bundled in the jar.

the development loot smoke check launches a real fabric client, verifies that fabric loot mixins are active, rolls all three supported chest tables for 128 seeds each, and runs the ancient-city item filter. it also checks that prediction does not invoke server loot events.

map checks cover negative tile coordinates, sampling bounds, seed/dimension/height changes, cancellation, cache reuse, end-city ship markers, and village starting points compared with full vanilla generation. native interaction checks cover panning, cursor-centered zoom, selection copying, dimension changes, and stopping work when leaving the map. the development smoke check also generates map tiles and structure dots in all three dimensions.

window checks cover preference round-trips, invalid values, damaged settings files, edge resizing, maximize/restore, sidebar resizing, zoom presets, detail and grid settings, and saving when the panel closes. the development smoke check also verifies that the native map requests and receives real biome tiles.

command-line stop checks with 2.1 million captured block observations measured 130–321 ms from stop to native return on an apple m3. the nether engine also passes repeated stop/restart checks and a known-seed recovery. these are local command-line checks, not live-client frame-rate measurements.
